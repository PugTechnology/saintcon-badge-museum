## Unpatched Firmware Compilation

`Firmware/Saintcon2020/main.cpp` is compiled **unpatched** (`0` lines modified in `upstream/Firmware/Saintcon2020/main.cpp`).

All hardware adaptation is performed via our own AVR shim headers in `emulator/cores/2020/platform/`:

1. **`platform/avr/io.h` & `platform/emu_2020.cpp` (16-bit `uint16_t` and AVR Integer Promotion)**:
   - Intercepts writes to `PORTA` (`AvrPortAReg`) and `PORTB` (`AvrPortBReg`) and reads from `PINB` (`AvrPinBReg`).
   - Within the `main.cpp` translation unit (`SAINTCON_2020_FW_TU`), `#define uint16_t avr_uint16_t` (`avr/io.h:189`) maps `uint16_t` to `struct avr_uint16_t { uint16_t v; ... }` (`sizeof(avr_uint16_t) == 2`). Every `uint16_t` variable in `main.cpp` (`millis`, `lastIntTime`, `lastDisplayUpdate`, `buttonDebounce`, `alternateDelay`, `alternate2Delay`, `circleDelay`, `lastTpUpdate`, `tpDelay`, and `binaryDelay`) is stored as a 16-bit unsigned value (`0..65535`) that wraps modulo 65536.
   - On AVR (`avr-g++`), `int` is 16 bits and `uint16_t` is `unsigned int` (16 bits); on WASM/x86_64, `int` is 32 bits, so a raw `unsigned short` would promote to signed 32-bit `int` under C++ integral promotion (`[conv.prom]`). `avr_uint16_t` overloads `+`, `-`, and relational operators so that `uint16_t` arithmetic with `uint16_t`, `uint8_t`, or `int` evaluates in 16-bit unsigned modulo-65536 arithmetic just as on AVR, while `millis - lastDebounceTime` (`main.cpp:484`, where `lastDebounceTime` is `uint32_t` at `main.cpp:476`) promotes `millis` to `uint32_t` just as on AVR.
   - Reading `volatile uint16_t millis` (`main.cpp:36`) calls `emu_2020_read_millis(&v)`. After 8 reads within the current millisecond, the 9th read advances badge time by 1 ms, invokes `ISR(TIM1_COMPA_vect)` at 1 kHz, and yields the cooperative fiber (`emscripten_fiber_swap` in WASM, `swapcontext` in native CLI) when the host frame budget is spent.
   - Other `int` arithmetic in `main.cpp` was checked for 16-bit vs 32-bit `int` differences: bit shifts (`1 << 0` through `1 << 7`) never reach bit 15, bitwise complements (`~(1 << n)`) are masked into `uint8_t`, loop counters (`for(int x = 0; x < 8; x++)`, `x < NUMLEDS - 1`) and `uint8_t` comparisons (`displayState > numStates`, `displayCounter > NUMLEDS * 2`, `tpCounter < displayState + 1`, `tpCounter > displayState + 2`) use small non-negative values (`0..17`, or `0..100` in Mode 3 Pulse at `main.cpp:255-265`), and `isButtonPressed()` (`main.cpp:473-489`) stores `0` or `4` in `previousButtonState` / `currentButtonState` and `0` or `1` in `sent`. None of those expressions differ between 16-bit and 32-bit `int`.
   - In `main.cpp:201`, Mode 0 (Ring) executes `LEDS[displayCounter - NUMLEDS] = 0;` when `displayCounter == 16`, writing one byte past `LEDS[8]` (`LEDS[8] = 0`). On the real badge that byte is unused RAM (per the review's look at the upstream hex). In both the native CLI (`emu-cli`) and WebAssembly (`core.wasm`) builds, `avr/io.h:172-186` places both `LEDS[8]` (`main.cpp:33`) and the immediately following `millis` (`main.cpp:36`) in `.bss.leds_isolated` with `aligned(64)`, so the byte `LEDS[8]` is unused padding in both builds. In `core.wasm`, `millis` starts 64 bytes after `LEDS`; in `emu-cli`, `millis` comes first and `LEDS` is last, before the next variable. `build.sh` checks both the native `emu-cli` symbol table and the WASM link map (`core_wasm.map`) and fails the build if the byte after `LEDS` belongs to another variable.
2. **LED Brightness From Real `PORTA` Writes (`emu_2020_on_porta_write`)**:
   - `ISR(TIM1_COMPA_vect)` (`main.cpp:448-471`) runs at 1 kHz (`1000000 / ((124 + 1) * 8)` at `main.cpp:99-106`), writing `PORTA = ledstate;` (`main.cpp:464`) on every 1-ms tick while stepping `pwmcounter += 5` (`1, 6, 11, ..., 96`, 20 ticks per 50 Hz PWM cycle).
   - `emu_2020_on_porta_write()` records a 20-slot sliding window of the real writes to `PORTA` and computes each LED's brightness (`D1..D8` on `PA0..PA7`) strictly from the fraction of those 20 `PORTA` writes in which bit `0..7` was `1`, mapped through the 21-point monotonic lookup table `kPwmCurve20[0..20]`. Because no hardware file specifies an LED colour (`value="LED"`), `emu_leds()` outputs a neutral warm-white RGB triple scaled by `kPwmCurve20`. `LEDS[]` is never read by the renderer.
3. **`set_sleep_mode` and `LONGPRESSTIME`**:
   - `main.cpp:77` calls `set_sleep_mode(SLEEP_MODE_PWR_DOWN)` and enables `PCIE1` / `PCINT10` (`main.cpp:78-79`) with an empty `ISR(PCINT1_vect)` (`main.cpp:491-493`), and `main.cpp:29` defines `#define LONGPRESSTIME 2000`. Neither `sleep_mode()` / `sleep_enable()` / `sleep_cpu()` nor `LONGPRESSTIME` is ever called or referenced anywhere else in `main.cpp`, so the firmware never enters sleep mode.
4. **Special Mode (`TP1` Held Low at Boot), 16-bit Wrap Behaviour, & `TP1` Pull-Up Toggles**:
   - At boot (`main.cpp:153`), `if((PINB & 1<<TP1PIN) == 0) specialModes();` checks whether `TP1` (`PB0`) is held low. When active, `specialModes()` (`main.cpp:495-558`) steps through `char messages[8][19]` (`main.cpp:499-506`) every `1001` ms (`if(millis > (lastDisplayUpdate + binaryDelay))` with `binaryDelay = 1000` at `main.cpp:498, 523`) and advances between the 8 messages when `SW1` (`PB2`) is pressed.
   - Because `millis`, `lastDisplayUpdate`, and `binaryDelay` are 16-bit `uint16_t`, when `lastDisplayUpdate` reaches `65065` (`>= 64536`), `(uint16_t)(lastDisplayUpdate + 1000)` wraps modulo 65536 to `529..999`. For `millis = 65065..65535` (471 ms, ~0.47 s every 65.536 s), `millis > (lastDisplayUpdate + binaryDelay)` is true on every loop pass, so the message display races until `millis` wraps to `0`.
   - At `main.cpp:87-90`, `DDRB |= 1<<TP2PIN;` configures `TP2` (`PB1`) as an output that is never written high, while `//DDRB |= 1<<TP1PIN;` (`main.cpp:89`) is commented out, leaving `TP1` (`PB0`) as an input. In both `main()` (`main.cpp:385-401`) and `specialModes()` (`main.cpp:540-556`), the loop toggles `PORTB` bit `TP1PIN` (`PB0`) every `1001` ms (`millis - lastTpUpdate > tpDelay` with `tpDelay = 1000`), which toggles the internal pull-up resistor on input `TP1` `displayState + 1` times (`1..8` pull-up toggles) followed by a pause.
5. **Hardware Board Files (`Hardware/*-KiCad.zip`)**:
   - In `Saintcon2020MainBoard.kicad_pcb`, `D1`–`D4` are mounted on the front copper layer (`F.Cu`) and `D5`–`D8` are mounted on the back copper layer (`B.Cu`, alongside battery holder `BT1`).
   - Upstream `README.md:2` states the badge holds 17 minibadges; `MinibadgeHoldersPanel.kicad_pcb` contains 13 `MinibadgeHolder` and 4 `MinibadgeHolder90` boards (17 total); `Saintcon2020MainBoard.kicad_pcb` has 7 slots (14 `MinibadgeSolderConnector` footprints), `Saintcon2020VerticalBoard.kicad_pcb` has 6 slots (12 `MinibadgeSolderConnector` footprints), and `Saintcon2020HorizontalBoard.kicad_pcb` has 4 `MinibadgeSolderConnector` footprints (2 slots).
