## 2. Summary of All Emulator Changes to `rp2040js` and Hardware View

Checked line by line against `emulator/cores/2022/src/badge2022.mjs`, the list below names every change the emulator makes to plain `wokwi/rp2040js` or to the firmware's view of hardware, with one line of why:

1. **8 MHz CPU clock (`cycleNanos = 125` instead of `8`):** Reduces Cortex-M0+ instruction volume by 15.625× while keeping `RPTimer` in nanoseconds so all `sleep_us` / `sleep_ms` / repeating-timer intervals stay real-time in the browser Worker.
2. **Second Cortex-M0+ core (`core1`) stepped in lockstep with `core0`:** Plain `rp2040js` instantiates only one `CortexM0Core`; the 2022 firmware runs a second entry point on Core 1 (it waits on `ledsEnabled` at `0x1000031a..0x10000320`, see 3.1) to charlieplex the 52 RGB LEDs while Core 0 runs game logic.
3. **Per-core IRQ routing (`mcu.setInterrupt`):** Routes `SIO_IRQ_PROC0` (IRQ 15) to Core 0, `SIO_IRQ_PROC1` (IRQ 16) to Core 1, and shared peripheral IRQs to both cores so inter-core mailbox interrupts reach the right core.
4. **ARMv6-M `SEV` (`0xbf40`) cross-core wake hook:** Plain `rp2040js` only logs `"SEV"`; waking both cores (`eventRegistered = true`, `waiting = false`) lets timer alarm callbacks (`0x100022d4`) wake a sleeping core from `WFE`.
5. **Watchdog reset loop guard (`mcu.onWatchdogTrigger`):** Counts watchdog triggers and clears `watchdog.enable` so a fault test does not spin in an infinite reset loop.
6. **`RPTimer` sub-microsecond alarm scheduling and past-target race guard (`0x40054`):** Accounts for `clock.nanos % 1000` when arming `TIMER_ALARM0..3` and immediately fires an alarm if `target <= nowMicros` at `0x10002fc8`, preventing a 71.5-minute 32-bit timer wrap when the 18 instructions between `0x10002f8e` and `0x10002fc8` span a microsecond boundary on 10–25 µs rainbow sleeps at 8 MHz.
7. **Unwritten flash left erased (`0xFF`) and `savedSectors` overlay (`0x1cc000`, `0x1cd000`):** Initializes the 16 MB flash buffer to `0xFF` outside the UF2 payload (`0x10000000..0x1000bf00`) so first boot sees erased save sectors, and overlays persisted 4 KB sectors at `0x1cc000` and `0x1cd000`.
8. **Active-LOW GPIO pull-ups on `GP15`, `GP16`, `GP17`:** Sets `GP15` (`UP`), `GP16` (`DOWN`), and `GP17` (`SELECT`) high (`true`) at power-on (or low when boot-holding `DOWN` or `SELECT`) to match the board's pull-up configuration.
9. **`SIO` GPIO pin-time integration (`0x10..0x2c`):** Integrates exact simulated nanoseconds spent driving each `(cathode, anode)` pair on `GP0..GP14` across a rolling 50 ms window and tracks `GP24`/`GP25` minibadge clock toggles.
10. **Per-core `SIO_CPUID` (`0x00`):** Returns `0` when accessed by Core 0 and `1` when accessed by Core 1 so SDK multicore and spinlock code can identify the active core.
11. **`SIO_GPIO_IN` (`0x04`) returning driven output values on output-enabled pins:** Plain `rp2040js` returns only external `inputValue` bits on `SIO_GPIO_IN`; combining `(inVal & ~oe) | (gpioValue & oe)` matches RP2040 pad loopback so the 500 ms timer callback can toggle `GP24` and `GP25` via `gpio_put(pin, !gpio_get(pin))`.
12. **Bidirectional `SIO` inter-core FIFOs (`0x50`, `0x54`, `0x58`) and IRQ 15/16 updates:** Implements the two 8-word mailboxes (`fifo0to1`, `fifo1to0`) and status flags required by `multicore_launch_core1` and `multicore_reset_core1`.
13. **Per-core `SIO` hardware divider (`0x60..0x78`):** Gives Core 0 and Core 1 separate hardware divider register sets so concurrent division on both cores does not clobber quotient/remainder state.
14. **Per-core `SIO` spinlock ownership tracking (`0x100..0x17c`):** Records which core acquired each hardware spinlock (`core0SpinLockMask`, `core1SpinLockMask`) so resetting Core 1 can release only locks held by Core 1 without ever dropping a lock held by Core 0.
15. **`PSM` (`0x40010`) Core 1 reset hook, FIFO clearing, and Core 1 spinlock grace:** Halts and resets Core 1 to the bootrom when `PSM_FRCE_OFF` bit 16 (`0x40010004`) is asserted, clears the inter-core FIFOs, and steps Core 1 up to 512 instructions if it is mid-critical-section (`PRIMASK=1` or holding a spinlock) before clearing `core1SpinLockMask` so Core 0 does not deadlock on `SPINLOCK18` (`0xd0000148`) at `0x10002652` during flash saves.
16. **`SSI` (`0x18000`) and `IO_QSPI` (`0x40018`) SPI flash command emulation:** Emulates chip-select framing and SPI commands `0x4b` (Read Unique ID -> `e6614103e715222a`), `0x20` (4 KB sector erase), `0xd8` (64 KB block erase), and `0x02` (256-byte page program) when `save_clues_flash` (`0x10000938`) and `save_cursors_flash` bit-bang the QSPI bus from RAM.
17. **`I2C0` (`0x29` ambient light sensor), `I2C1` (`0x20..0x27` minibadge NACK), and `IC_RAW_INTR_STAT.TX_EMPTY` on NACK:** Responds to `I2C0` address `0x29` with ambient light reading `250` (`> 100` threshold) so LEDs stay enabled (`[0x20000788] = 1`), NACKs unconnected `I2C1` minibadges, and asserts `TX_EMPTY` (`0x10`) on NACK so `i2c_write_blocking_internal` (`0x10008ebe`) does not hang polling `IC_RAW_INTR_STAT`.
18. **Emulator-level `stdio` hooks (`0x10006228`, `0x10006428`) and bootloader watch (`0x10000ed2`):** Intercepts `getchar_timeout_us` (`0x10006228`) and `stdio_usb_out_chars` (`0x10006428`) in default `'hook'` mode to avoid 1 kHz TinyUSB SOF polling overhead at 8 MHz, and detects USB bootloader entry at `0x10000ed2`.
19. **25 ms minimum button hold and release gap (`MIN_BUTTON_HOLD_NANOS`, `MIN_BUTTON_GAP_NANOS`):** Holds each UI button press low for at least 25 ms of simulated time (and spaces queued taps by 25 ms high) so a press and release that arrive from the browser in the same 33.3 ms Worker frame do not cancel out in 0 ns before a CPU instruction executes.
20. **Explicit stand-in `sendWhenBlinkEven` option in `sendSerial`:** Raw `sendSerial(str)` delivers bytes immediately; only the web page's kiosk stand-in `Visit` passes `{ sendWhenBlinkEven: true }`, which waits until `newClueBlinkCounter` (`0x20001c1c`) is even in Mode 0 (`0x20001c04 == 0`) so a visitor clicking `Visit` twice within 15.25 s does not trigger the firmware's odd-blink XOR quirk.

## 3. Hardware Map & Firmware Architecture (from UF2 Disassembly)

### 3.1 Charlieplexed RGB LED Matrix (`GP0..GP14`, 52 RGB LEDs = 156 Channels)
Core 1 (`0x1000031a..0x10000320`) continuously scans 3 LED tables in RAM (`21` Suspects at `0x20000888` copied from flash `0x1000b60c`, `21` Attacks at `0x20000590` copied from flash `0x1000b314`, and `10` Rooms at `0x20000790` copied from flash `0x1000b514`). Each LED entry is `24` bytes (`3` color channels × `8` bytes: `uint8_t cathode_pin`, `uint8_t anode_pin`, `uint16_t pad`, `uint32_t brightness` in `0..2550`).
- When `[0x20000788]` (`ledsEnabled`) is `0`, `core1_entry` (`0x1000031a..0x10000320`) spins with all GPIO outputs disabled (`GP0..GP14` hi-Z).
- When `[0x20000788]` is `1` and a channel's `brightness > 0`, Core 1 enables output on `(1 << cathode) | (1 << anode)`, drives `1 << anode` high and `cathode` low, sleeps for `brightness / 50` µs (in Mode 0, active channels use `brightness = 2500` -> `50 µs`), and then clears all `GP0..GP14` outputs.

### 3.2 Buttons (`GP15`, `GP16`, `GP17`, Active-LOW) & 25 ms Minimum Hold
- `GP15` = **UP**, `GP16` = **DOWN**, `GP17` = **SELECT**.
- **Boot-hold checks in `main`:**
  - If `GP17` (`SELECT`) is LOW at boot (`0x10000ec6..0x10000ed2`), the firmware jumps into the RP2040 bootrom `reset_usb_boot` entry (`blx r3` at `0x10000ed2`).
  - If `GP16` (`DOWN`) is LOW at boot, or if the clue flash sector at `0x101cc000` is erased (`0xffffffff`), `main` calls `rgb_self_test` (`0x10000a3c..0x10000b2e`). The self-test lights all 52 LEDs Red (`500 ms`), Green (`500 ms`), and Blue (`500 ms`) in an infinite loop (`0x10000b2e: b 0x10000a62`); **the self-test never ends by itself**. On an erased save sector (`0xffffffff` at `0x101cc000`), `main` first calls `save_clues_flash(0)` (`0x10000938`) to program `0x00000000` to `0x101cc000` before calling `rgb_self_test` (`0x10000a3c`), so pressing **Reset Badge** boots into the notepad.
- **Main-loop button polling (`0x10001906..0x10001928`) and why `MIN_BUTTON_HOLD_NANOS` is 25 ms:**
  - At 8 MHz in idle Mode 0, Core 0 reaches `0x10001906` `94,513` times per second (measured median interval `8.5 µs`, 99th-percentile `191.4 µs`, maximum idle interval `599.3 µs`). Even a raw `250 µs` (`0.25 ms`) GPIO pulse on `GP16` registers immediately.
  - In the browser UI, however, `pointerdown` and `pointerup` events from a quick click or tap are sent via `Worker.postMessage` and can both arrive before the same `30 fps` (`33.3 ms`) `step_frame` tick runs. Without a minimum hold, the Worker would set the pin LOW and immediately back HIGH at the exact same simulated nanosecond (`0 µs` pulse width) before executing a single CPU instruction. Holding each press low for at least `25 ms` of simulated time (and enforcing a `25 ms` high gap between queued taps) ensures every tap spans at least one poll and release-wait loop while long holds stay low until released.
- **SELECT button in post-win modes (`0x100013a4`):**
  - The `SELECT` handler checks `displayMode` (`0x20001c04`); when `displayMode == 0`, it toggles `activeCategory` (`0x20001d44`) between `0` (Suspects) and `1` (Attacks) at `0x100013a4` (Rooms has no user cursor). When `displayMode != 0` (Modes 1–5 after winning), `SELECT` branches straight back to the main loop and does nothing.

### 3.3 Flash Persistence (`0x1cc000` & `0x1cd000`) & Core 1 Spinlock Race
- **`save_clues_flash` (`0x10000938`)** and **`save_cursors_flash`** erase and program 4 KB sectors at flash offsets `0x1cc000` (`0x101cc000`: `[clueWordRaw, suspectsMask, attacksMask, roomsMask]`) and `0x1cd000` (`[displayMode, suspectsCursor, attacksCursor, roomsCursor, gameWon, winSuspectsMask, winAttacksMask, winRoomsMask]`).
- **Core 1 reset spinlock race (`0x10002652`):**
  - Before erasing/programming flash, the firmware calls `multicore_reset_core1()`, which asserts `PSM_FRCE_OFF` bit 16 (`0x40010004`). Meanwhile, Core 1 calls `sleep_us(50)` 20,000 times per second, acquiring and releasing the default `alarm_pool` hardware spinlock (`SPINLOCK18` at `0xd0000148`) with interrupts disabled (`PRIMASK=1`).
  - On real RP2040 hardware, resetting Core 1 via `PSM_FRCE_OFF` does **not** clear `SIO` hardware spinlocks; if Core 1 is reset while holding `SPINLOCK18`, the lock stays held and Core 0 deadlocks in `save_clues_flash` / `save_cursors_flash` when it calls `sleep_ms(10)` and spins forever waiting for `SPINLOCK18` at `0x10002652`.
  - This is an SDK race in the firmware (`multicore_reset_core1` while Core 1 uses the shared default alarm pool). Running the CPU at 8 MHz (`125 ns/cycle`) instead of 125 MHz (`8 ns/cycle`) makes the race about **15 times more likely**: over a measured `200 ms` window in Mode 0, Core 1 holds an `SIO` spinlock during **`12.45%`** of its executed instructions at 8 MHz (`113,022 / 908,177` instructions) versus **`0.82%`** at 125 MHz (`119,002 / 14,570,025` instructions), a **`15.24×`** ratio.
  - Whether real badges ever froze from this race on hardware is unknown. The emulator hides this race on purpose so the badge does not freeze during cursor saves or clue receipts: when `PSM_FRCE_OFF` bit 16 is asserted, `badge2022.mjs` lets Core 1 finish up to 512 instructions if `core1.PRIMASK || core1SpinLockMask !== 0` and then clears only `core1SpinLockMask` (preserving any spinlock held by Core 0, such as `SPINLOCK5` at `0xd0000114` in `test.mjs`).

### 3.4 I2C Peripherals (`I2C0` Ambient Light Sensor & `I2C1` Minibadge Scan)
- The main loop polls `I2C0` address `0x29` about every 50 ms: the check at `0x1000189c..0x100018a2` is `millis - last > 50` and branches to `0x10001dc2..0x10001df4` (via `read_ambient_light` at `0x100020c0`), which ends with a branch back to `0x100018a4`. A separate 500 ms repeating timer callback (see section 2, item 11) scans `I2C1` addresses `0x20..0x27` and toggles the `GP24`/`GP25` minibadge clock pins.
- If the 16-bit ambient light reading on `I2C0` `0x29` (registers `0x88..0x8b`) is in `1..100`, the firmware writes `0` to `[0x20000788]` (`ledsEnabled`), blanking all LEDs. If the reading is `0` or `> 100`, it writes `1` to `[0x20000788]`. `badge2022.mjs` defaults the sensor reading to `250` (`> 100`).

### 3.5 USB Serial Kiosk Protocol (`0x100018a4..0x100018a8`, `0x100006c8`)
- In the main loop (`0x100018a4..0x100018a8`), Core 0 calls `getchar_timeout_us(0)` (`0x10006228`, hooked via `STDIO_HOOKS.GETCHAR_TIMEOUT_US`) and `stdio_usb_out_chars` (`0x10006428`, referenced by the descriptor at `0x20000c20` and hooked via `STDIO_HOOKS.STDIO_USB_OUT_CHARS`).
- **Commands:**
  - `kiosk:ping\n\r` -> replies `badge:pong`.
  - `kiosk:hi\n\r` -> calls `send_badge_message(1)` (`0x100006c8`).
  - `kiosk:<34-hex-rotated><2-hex-chk>\n\r` -> validates length (`invalid clue length from kiosk`), checksum (`incorrect checksum`), and 64-bit flash unique ID (`serial number doesn't match`), then prints `new clue!`, updates RAM masks (`0x20001c14`, `0x20001c0c`, `0x20001c10`, or win masks `0x20001ec8`, `0x20001ec0`, `0x20001ec4` and `gameWon` at `0x20001f00` when `clueNum` at `0x20001754` is `0xFF`), saves flash, and calls `send_badge_message(2)`.
- **Why trailing stack bytes follow `badge:<36-hex>` (`send_badge_message` at `0x100006c8`):**
  - `send_badge_message` (`0x100006c8`) allocates a 40-byte stack frame (`push {r4, r5, r6, lr}; sub sp, #0x28`), writes the 36 rotated ASCII hex characters into `char output[36]` at `sp+0x04..sp+0x27` **without a NUL terminator**, and calls `printf("badge:%s", output)`.
  - `printf` reads past `sp+0x27` into the saved `r4` word on the stack at `sp+0x28..sp+0x2b` until it hits a `0x00` byte:
    - When `kiosk:hi` or `kiosk:<clue>` is processed in `main`, `r4` holds the low 32 bits of the boot-time `time_us_64()` timestamp read at `0x10000ffa` (`0x00004a20` at 8 MHz -> bytes `0x20, 0x4a, 0x00` -> `" J"`; `0x0000293f` at 125 MHz USB -> bytes `0x3f, 0x29, 0x00` -> `"?)"`; `0x00004255` on a warm reset -> `"UB"`).
    - When `UP` (call at `0x1000129e`) or `DOWN` (call at `0x1000138a`) calls `send_badge_message(1)` on button release, `r4` holds the loop counter / state from the button handler, so `UP` and `DOWN` also print trailing stack bytes in the serial log (such as `\xff`) before the first zero byte in `r4`.
- **Firmware odd-blink clue quirk & stand-in `sendWhenBlinkEven`:**
  - When a normal clue (`clueNum != 0xFF`) arrives in Mode 0 (`0x20001c04 == 0`), `main` sets `new_*_xor = old_mask ^ new_mask` and sets `newClueBlinkCounter` (`0x20001c1c`) to `61` (`0x3d`, `61 × 250 ms = 15.25 s`), assuming all previously cleared LEDs in `old_mask` are currently ON (`2500`) in the RAM LED tables.
  - During that 61-tick blink, the firmware toggles each LED in the xor masks from its **current** brightness, not from the counter's parity: the Suspects loop at `0x10001570..0x100015b4` (table `0x20000888`, xor mask `0x20001c24`) reads each blinking LED's brightness word (`0x1000159e..0x100015a4`); if it is non-zero it writes `0` (`0x1000157a..0x10001580`), and if it is zero it writes the lit value (`0x100015a6..0x100015b2`). The counter parity only says which tick the blink is on; it does not set the LED.
  - UP and DOWN each relight every cleared Suspect and Attack LED. The UP handler loops over all 21 rows at `0x1000124e..0x10001272` (Suspects: tests `suspectsMask` at `0x20001c14`, stores the lit value from `0x2000078c` into the green brightness word at table `0x20000888 + row*24 + 0x14`, at `0x10001270`) and at `0x10001274..0x10001298` (Attacks: `attacksMask` at `0x20001c0c`, table `0x20000590`, store at `0x10001296`). The DOWN handler has the same pair, with stores at `0x1000135c` and `0x10001382`. Rooms are not redrawn. If a press lands while blinking Suspect and Attack LEDs are dark, the redraw lights them, the next blink tick turns them off, and their blink phase is inverted for the rest of the 15.25 s. Measured in the core: a press while the counter is odd leaves 4 of the clue's 5 LEDs dark after the blink ends, and a press while it is even leaves all 5 lit. The Room LED keeps its phase either way, because no button redraws it. The same quirk affects a second clue that arrives mid-blink, because `old_mask ^ new_mask` is built while some LEDs are dark.
  - A real hardware kiosk would see this exact quirk only if a badge were plugged into a second kiosk (or sent a second clue) within about `15 s` (`15.25 s`) of the previous clue while the previous clue was still blinking on an odd tick.
  - In `badge2022.mjs`, raw `sendSerial(str)` (`test.mjs` and `core.js`) delivers bytes to the firmware immediately without holding, so raw tests and the 8 MHz vs 125 MHz parity suite exercise the unpatched firmware behavior. Only the web page's kiosk stand-in `Visit` passes `{ sendWhenBlinkEven: true }`, which waits in `evenBlinkSerialQueue` when `rx_state` (`0x20001d50`) is `0` and `newClueBlinkCounter` (`0x20001c1c`) is odd, so two Visits in a row do not trigger the quirk. It does not guard against badge button presses during a blink; the page tells visitors to leave the buttons alone for about 15 s, and **Reset Badge** redraws every LED from the save.
- **Millis counter (`0x20001ed4`):** Holds the firmware's 32-bit millisecond timestamp updated in the main loop.
